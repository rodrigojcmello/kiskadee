# Generated Showcase Registries Git Policy

Status: technical debt / open decision.

## Context

`@kiskadee/web-builder` generates Showcase TypeScript registries under:

```txt
packages/showcase/registry/generated/
```

The file that made this debt visible is:

```txt
packages/showcase/registry/generated/design-systems.registry.generated.ts
```

That file is generated by `packages/web-builder/scripts/generate-showcase-registry.ts` from
`manifest.json` files. It is consumed through the hand-written entrypoint:

```txt
packages/showcase/registry/design-systems.registry.ts
```

The current Showcase build path already runs generation before `next build`:

```txt
pnpm --filter @kiskadee/showcase build
  -> pnpm run build:artifacts
  -> @kiskadee/web-builder build-sync-generate
  -> next build
```

So production builds that use the package script should regenerate the registry before Next
compiles the app.

## Technical Debt

The repository has not made an explicit policy decision about whether generated Showcase registry
files should be committed.

Keeping generated registries in Git has useful properties:

- clean checkouts can run `next dev`, type checking, or editor tooling without first running the
  builder;
- diffs show when a schema or manifest change affects the Showcase-facing registry;
- deploy systems that do not run the expected package scripts still have the generated modules
  present.

But committing generated registries also has costs:

- diffs include generated churn that can hide the authored source change;
- stale generated files can be committed when the source schema changed but generation was not
  rerun;
- merge conflicts can appear in files that no one should edit by hand;
- reviewers must remember which files are source of truth and which are derived outputs.

The repo needs a deliberate answer instead of discovering this policy through accidental diffs.

## Question

Should `packages/showcase/registry/generated/**` be committed, or should it be ignored and treated
as a local/build artifact?

This question should include all generated Showcase registries, not only
`design-systems.registry.generated.ts`:

- `colors.registry.generated.ts`;
- `css.registry.generated.ts`;
- `design-systems.registry.generated.ts`.

It should also be decided separately from `packages/showcase/public/build/**`, because public build
artifacts have different runtime and deployment behavior.

## Impact If Git-Ignored

Adding `packages/showcase/registry/generated/**` to `.gitignore` would make generated registry files
local artifacts.

Expected benefits:

- smaller source diffs for schema/component changes;
- less generated-file merge conflict noise;
- clearer source ownership if the build always regenerates before use.

Expected costs and required follow-up:

- clean checkout workflows must run `pnpm --filter @kiskadee/web-builder run generate` or
  `pnpm --filter @kiskadee/showcase build:artifacts` before importing Showcase registry entrypoints;
- `next dev` must keep guaranteeing a pre-dev generation step, because the hand-written registry
  entrypoints statically re-export generated modules;
- type checking and editor diagnostics may fail before generation with missing-module errors;
- CI must validate that no command reaches `next build` or TypeScript checks before registry
  generation;
- contributors may need a clearer error or bootstrap script when generated registries are missing.

The key technical issue is that these registries are TypeScript modules, not runtime JSON fetched
from `/public/build`. If the generated files are absent, static imports can fail before the
Showcase app reaches runtime.

## Next Showcase Publish Side Effects

If the deployment command is the current package script:

```bash
pnpm --filter @kiskadee/showcase build
```

then ignoring generated registries should be viable in principle, because `build:artifacts` runs
before `next build`.

However, ignoring them can break or complicate publish/deploy paths when:

- a platform runs `next build` directly inside `packages/showcase`;
- a platform restores a cached `.next` or workspace state without regenerating registry files;
- a developer previews a production build from a clean checkout using a shortened command;
- the package script order changes and `next build` starts before `build:artifacts`;
- the Showcase package is ever extracted, published, or deployed without the web-builder package and
  preset sources available.

There is also a review trade-off: if generated registries are ignored, schema changes that alter
Showcase navigation, manifests, segments, themes, or component metadata will no longer be visible in
Git diffs unless validation explicitly inspects generated output.

## Proposed Investigation

Before changing `.gitignore`, answer these questions with a small spike:

1. From a clean checkout with `registry/generated` deleted, does
   `pnpm --filter @kiskadee/showcase dev` fully regenerate files before Next imports them?
2. From that same clean checkout, does `pnpm --filter @kiskadee/showcase build` pass on CI-like
   settings?
3. Does `pnpm exec tsc -p packages/showcase/tsconfig.json --noEmit` need a generation pre-step?
4. Do Vercel or other deployment configs call the package `build` script, or can they call
   `next build` directly?
5. Do we want generated registry diffs as review evidence for schema/manifest changes, or should
   validation commands provide that evidence instead?

## Possible Outcomes

### Keep Committing Generated Registries

Use this if zero-bootstrap development and visible generated diffs are more valuable than reducing
churn.

If this path is kept, the repo should document that any schema/manifest change must regenerate and
stage the affected registry files.

### Git-Ignore Generated Registries

Use this if the project wants generated registries to behave like build artifacts.

If this path is chosen, the repo should also:

- add a reliable pre-dev/pre-build generation path for every Showcase command that imports the
  registry entrypoints;
- make CI run the same generation path before Showcase type checks and builds;
- document the bootstrap command for clean checkouts;
- consider making the hand-written registry entrypoints fail with a clear message when generated
  files are missing.

## Temporary Guidance

Until this is decided, keep the current behavior:

- generated Showcase registry files may appear in diffs;
- do not edit `packages/showcase/registry/generated/**` manually;
- regenerate them through `@kiskadee/web-builder` when schema, manifest, segment, theme, or
  component metadata changes affect Showcase.
