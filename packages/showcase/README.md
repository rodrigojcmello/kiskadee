## Showcase

The `showcase` is a Next.js app used as **tooling/viewer** for the Design Systems in this monorepo.
It is used to:

- Select a Design System (preset) and browse components
- Load CSS and JSON maps generated by `@kiskadee/web-builder`
- Inspect artifacts (e.g. `manifest.json`, `colors.json`, `segments.json`, `core.kiskadee.json`, etc.)

### Local development

Run the showcase from the monorepo root:

```bash
pnpm --filter @kiskadee/showcase dev
```

This command is the local development entrypoint. It runs this sequence:

```txt
1. Build @kiskadee/fonts, @kiskadee/icons, @kiskadee/react-headless, and
   @kiskadee/react-components once, while regenerating the @kiskadee/web-builder artifacts.
2. Start the @kiskadee/react-components structural style watcher.
3. Start next dev --webpack for the showcase.
```

The showcase consumes `@kiskadee/react-components` from `dist`, matching the production package
contract. During local development, the style watcher keeps `dist/**/*.css` updated when files under
`packages/components/react/src/**/*.scss` change.

Webpack is explicit in the Showcase development and production-build entrypoints because Next.js
16 Turbopack can remain indefinitely in compilation for this monorepo. This affects the compiler
only; package builds, generated artifacts, and the application runtime contract remain unchanged.

Notes:

- Editing structural Sass does not require a manual component rebuild while `showcase dev` is
  running.
- Editing TypeScript/TSX in `@kiskadee/react-components` still requires rebuilding/restarting the
  package because the dev watcher only handles structural Sass.
- The style watcher uses polling. To tune it:

```bash
KISKADEE_STYLE_WATCH_INTERVAL_MS=250 pnpm --filter @kiskadee/showcase dev
```

Open `http://localhost:3000`.

For a fully clean local start, use:

```bash
pnpm --filter @kiskadee/showcase dev:fresh
```

This first runs `clean:dev`, which clears `@kiskadee/react-headless` dist output,
`@kiskadee/react-components` dist output, and generated `@kiskadee/web-builder` / Showcase
artifacts before starting the normal `dev` flow.

### Production build / publishing

Build the Next.js showcase from the monorepo root:

```bash
pnpm --filter @kiskadee/showcase build
```

This command runs the publication build sequence:

```txt
1. pnpm run build:components
   -> builds @kiskadee/fonts online integration JS and types into dist
   -> runs build:headless
   -> builds @kiskadee/react-headless JS/types into dist
   -> builds @kiskadee/react-components JS, types, and component CSS into dist

2. pnpm run build:artifacts
   -> runs @kiskadee/web-builder build-sync-generate
   -> syncs generated artifacts into packages/showcase/public/build

3. next build --webpack
   -> creates the optimized production Next.js build
```

To serve the built app locally:

```bash
pnpm --filter @kiskadee/showcase start
```

### Artifact build flow (where Showcase data comes from)

Showcase does not “compile” tokens/palettes by itself. It **consumes artifacts** generated by `@kiskadee/web-builder`.

Typical flow:

```bash
pnpm -C packages/web-builder run build
pnpm -C packages/web-builder run sync
pnpm -C packages/web-builder run generate
```

- `build`: generates artifacts into `packages/web-builder/build/<designSystemKey>/...`
- `sync`: copies artifacts into Showcase at `packages/showcase/public/build/<designSystemKey>/...`
- `generate`: generates Showcase TypeScript registries based on `manifest.json`
- `packages/showcase build`: runs component build, artifact pipeline, and `next build`

## Folder structure

### `app/`

Next.js App Router.

- Defines `layout`, routes and pages
- Usually consumes components from `components/` and `k-components/`
- `/colors` renders every primitive family and variant discovered in the active Design System's
  published `colors.json`. It loads the referenced Light and Dark files from `colors/` and never
  imports preset source modules. Functional `subtle` and `vivid` references are inspection markers;
  the page does not redefine them.
- `/icons` exercises the public `@kiskadee/react-components` Icon contract with a local sample of
  30 common glyphs imported directly from `lucide-react`, plus the Social brand family from
  `@kiskadee/icons`. The Lucide sample is documentation data, not a Kiskadee icon library. Social
  exports ending in `Icon` remain dynamically discoverable. The route starts from the canonical
  `neutral` intent and uses `s:lg:3` as its inspection size; the component default remains
  `s:md:1`.

### `components/`

Showcase UI components.

- Can be “product-like” components (pages, panels, viewers)
- May or may not use components from `k-components/`
- Usually contains Showcase-specific logic (e.g. loading and rendering artifacts)
- Does not own reusable SVG artwork. Import interface glyphs directly from the selected provider
  and brand marks from `@kiskadee/icons`; keep local artwork only when it is intrinsically coupled
  to one Showcase-only visualization.

### `k-components/`

Project “headless + styled” components.

- Wrappers around headless components (e.g. `@kiskadee/react-headless`)
- Provide the Showcase styling/skin and a more ergonomic API for internal use
- Example: `Select` (consistent selection control in Showcase)
- Showcase-only selection patterns should stay here or in `components/`; do not add a new Headless
  primitive when an existing internal control already satisfies the interaction contract.

### `hooks/`

React hooks for Showcase loading/state rules.

Common examples:

- Design System/segment/theme selection
- `manifest.json` loading
- Global theme class synchronization (`light`/`dark`)

### `registry/`

TypeScript registries used by Showcase to discover and load build artifacts.

- `registry/generated/`: **generated** files
- `registry/*.registry.ts`: hand-written “entrypoint” files that **re-export** the generated ones
  - goal: simplify imports and make it clear what is generated vs hand-written

Main registries:

- `design-systems.registry`: Design System list and metadata (from `manifest.json`)
- `css.registry`: CSS URLs for `core`, `effects` and palettes by `segment|theme`
- `colors.registry`: loaders for `colors.json` and primitive scales in `colors/<file>.json`

> Note: registries are generated by `packages/web-builder/scripts/generate-showcase-registry.ts`.

### `public/build/`

Artifacts **copied** from `@kiskadee/web-builder` and served statically by Next.

Typical structure per Design System:

- `public/build/<designSystemKey>/manifest.json`
- `public/build/<designSystemKey>/core.kiskadee.css`
- `public/build/<designSystemKey>/core.kiskadee.json`
- `public/build/<designSystemKey>/<segment>.<theme>.kiskadee.(css|json)`
- `public/build/<designSystemKey>/colors.json`
- `public/build/<designSystemKey>/colors/<colorFile>.json`

These files are loaded via `fetch` (e.g. `utils/build-artifacts.client.ts`).

### `utils/`

Shared utilities for Showcase.

- Helpers for loading artifacts from `/public/build` (e.g. `loadJsonFromBuild`)
- Formatting/parsing helpers

## Important conventions

- Showcase is an artifact consumer: if something is “missing”, run `web-builder build-sync-generate`.
- Online font providers and preset font integrations belong to `@kiskadee/fonts`; the font select
  is projected from its public lazy catalog rather than a Showcase-owned list. The active artifact
  supplies the recommendation and preparation outcomes explain local-versus-online resolution.
- The Colors foundation route inspects all published primitives, including variants that are not
  currently mapped to a global semantic or component intent. Darker reuses the primitive Dark
  scale and is not rendered as a duplicate third track.
- Background controls distinguish canonical surfaces published in
  `components/card.kiskadee.json` from diagnostic Stress Test colors. See
  [Background Surface Catalogs](docs/definitions/background-surface-catalogs.md).
- Initial and fallback theme selection prefers `light` whenever the active preset exposes it. A
  valid theme explicitly persisted by the user still takes precedence.
- Generated registries are outputs: do not edit files under `registry/generated/` manually.
- Interface glyphs come directly from the chosen provider, currently `lucide-react`; reusable
  brand marks belong to `packages/icons` and use direct
  `@kiskadee/icons/social/<Icon>` imports.
- For deployment builds (for example on Vercel), `pnpm build` inside `packages/showcase`
  already runs `@kiskadee/web-builder` `build-sync-generate` before `next build`.
